# VibeSec Guardian v1.1.1 release preparation

## VibeSec Guardian v1.1.1 — Managed local scanning and release-signing compatibility

These notes prepare v1.1.1 under `Unreleased`; they do not claim the release has been published. The existing v1.1.0 tag and GitHub release remain unchanged.

v1.1.1 carries the managed local scanning functionality that closes the execution gap between AppSec Guardian guidance and VibeSec Guardian’s real scanners. An installed skill can acquire a pinned consumer runtime, install or reuse a verified platform toolchain outside the application repository, execute a real Minimal or Standard scan, validate sanitized artifacts, and summarize actual scanner evidence. No sibling source checkout, preinstalled CLI, existing GitHub Actions workflow, or previous result is required.

Highlights:

- Skill-driven real Minimal and Standard scanner execution after explicit download/network disclosure and approval.
- Exact verified scanner installation with versioned persistent user caches, safe archive extraction, atomic publication, cache revalidation, and Opengrep Sigstore verification.
- Native Linux x86_64, macOS arm64, and macOS x86_64 profile support; macOS arm64 is the primary v1.1 local acceptance platform.
- Managed `vibesec scan --install-tools` with explicit cache/results/network options and unchanged `--tool-dir` compatibility.
- Pre-approval disclosure that the skill is small but managed scanner caches may consume several hundred megabytes; Standard may exceed 600 MB and Checkov may require a separately stored Docker image.
- Deterministic stderr-only runtime and scanner installation progress, verified-cache reuse reporting, and an uncontaminated final JSON object on stdout.
- Clear separation between assessment-only guidance, immediate local scanning, and GitHub Actions adoption for continuous CI.
- Private temporary raw output with only sanitized normalized, coverage, policy, report, finding-intelligence, inventory, and applicable SBOM artifacts retained.
- Scanner network disclosure: Trivy may fetch or update its official vulnerability database; Standard online OSV may send package identifiers, versions, ecosystems, and file hashes to OSV.dev or deps.dev. Offline OSV still requires a caller-provisioned validated database.
- Release signing and verification now share a signature-bundle-specific strict JSON policy. Legitimate large Cosign certificate or transparency strings are accepted within an explicit 2,000,000-character field limit and the existing 2 MiB total file limit.
- Duplicate keys, malformed UTF-8 or JSON, BOMs, non-finite numbers, excessive depth or item counts, control characters, and unsafe or oversized bundle files remain fail-closed. A rejected bundle is never published partially.

Release finalization:

- `skills/appsec-guardian/runtime.json` intentionally remains pinned to the last verified v1.1.0 runtime during preparation.
- The final v1.1.1 bundle URL and SHA-256 will be recorded only after the trusted release-candidate workflow produces and verifies the deterministic bundle.

Remaining limitations:

- Linux arm64, Windows-native, and complete-profile container execution are not supported.
- Checkov still requires Docker when supported IaC is applicable; missing Docker is a blocking tool error.
- Optional image scanning still requires an explicitly supplied immutable digest in an eligible trusted context.
- DAST, API testing, authenticated testing, and fuzzing remain separate opt-in capabilities.
- Scanner and maintained-rule coverage is incomplete; verified installation and a clean configured scope do not prove an application is secure.
